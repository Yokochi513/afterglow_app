# ADR 0001: 投稿画像プレビューのサムネイルに cacheWidth/cacheHeight を使用する

## ステータス

承認（2026-09-08）

## コンテキスト

Issue #71: iPhoneから画像を8枚一気に追加すると、投稿ダイアログ（Web）が落ちることがある。

原因を調査したところ、`PostAddDialog`（`lib/widgets/post_add_dialog.dart`）の画像選択直後のプレビュー表示に問題があった。

- 圧縮（`ImageService.compressImage`。短辺2048px・品質85%）は投稿確定時（`PostService.createPost`）にのみ実行され、選択直後のプレビュー（メイン1枚表示・サムネイル一覧の両方）は圧縮前の元解像度バイト列（`_previewImageBytes`）をそのまま `Image.memory` に渡している。
- `Image.memory` は `cacheWidth`/`cacheHeight` を指定しない限り元画像の解像度でデコードする。サムネイル（表示は64×64px相当）であっても、この指定がなければ元解像度のままデコードされる。
- サムネイル一覧（`_buildThumbnailStrip`）は選択済み画像すべてを同時に横並びで表示するため、選択枚数分（最大10枚）のデコード済みビットマップが同時にメモリへ乗りうる。iPhoneの写真（12MP前後、4032×3024px）を想定すると、デコード後1枚あたり約46MB、8枚で約370MBに達し、モバイルブラウザのタブメモリ上限を圧迫してクラッシュに至ったと考えられる。
- メイン側の1枚表示プレビューは `PageView.builder` により基本的に表示中の1枚のみがデコードされるため、サムネイル一覧側がメモリ消費の支配的な要因である。

## 検討した選択肢

1. **サムネイル専用の縮小バイト列を別途生成する**（`flutter_image_compress` 等でサムネイルサイズに圧縮したコピーを保持する）
2. **`Image.memory` の `cacheWidth`/`cacheHeight` を指定し、デコード時点で縮小させる**

選択肢1は、画像を選択するたびに追加の圧縮処理が走るため端末側のCPU/バッテリーを消費し、「元バイト列」と「サムネイル用バイト列」を二重に管理する必要が生じる。

選択肢2は、Flutter/Skiaのデコーダがネイティブに縮小デコードをサポートしており、追加の圧縮パスや状態管理を必要とせずにメモリ削減効果を得られる。

## 決定

サムネイル一覧の `Image.memory` に、表示サイズ（`_thumbnailSize`）へ端末の `devicePixelRatio` を掛けた物理ピクセルサイズを `cacheWidth`/`cacheHeight` として指定し、デコード時点で縮小させる。

サムネイル専用の圧縮バイト列は新たに作成せず、選択直後の元解像度バイト列（`_previewImageBytes`）をそのまま流用する。投稿時の圧縮処理（`ImageService.compressImage`）は変更しない。

## 影響（Consequences）

- サムネイル一覧のデコード後メモリが表示サイズ相当まで縮小され、複数枚選択時のクラッシュリスクが大幅に下がる。
- メイン1枚表示プレビュー（`PageView.builder`）は本対応の対象外。大きな画像を表示している間は、その1枚分のデコードメモリ（最大で約46MB程度）は引き続き発生する。将来的に同様の問題が再発する場合は、メイン側にも `cacheWidth`/`cacheHeight` の指定を検討する。
- サムネイルの実際のデコード解像度は端末の `devicePixelRatio` に依存するため、極端に高DPRの端末では縮小効果がやや小さくなる。
