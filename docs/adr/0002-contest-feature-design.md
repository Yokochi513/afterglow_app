# ADR 0002: コンテスト機能（匿名投稿・投票）の設計

## ステータス

承認（2026-09-08）

## コンテキスト

Issue #69: コンテスト機能を追加したい。要件は次の3点のみが記載されており、詳細設計（`docs/詳細設計.md`）には未記載の新規機能領域（PS_01〜PS_09 のいずれにも該当しない）。

- 匿名投稿
- 投票
- 投稿に対してコメントができる（コメント主は把握可能）

要件が抽象的なため、実装に先立ち以下の論点についてユーザーと協議し、決定した。本 ADR はその決定内容の記録である。詳細設計の更新自体は本 ADR の対象外とし、実装 Issue 側で反映する。

## 検討した論点と決定

### 1. 運営権限

コンテストの作成は承認済みメンバー（`approved == true`）なら誰でも可能とする。管理者限定にはしない。

更新・削除は作成者（`creatorId`）本人、または管理者のみ許可する。`Event`（`organizerId`）と同一のパターン。

コンテストの「終了」は作成者による明示操作ではなく、後述のとおり日時から自動算出するため、作成者が行う操作は実質的に「作成」「締切前の編集」「削除」のみとなる。

### 2. データモデル：投稿は `posts` に一元化し、コンテスト用フィールドを追加

投稿方法を二系統に分けると作成 UI・サービス層・フィード/マップ表示ロジックが二重管理になり運用負荷が高い。そのため専用の `entries` コレクションは設けず、コンテストへのエントリーも通常投稿と同じ `posts` コレクション・同じ `PostService`/投稿ダイアログで作成する。投稿時に「コンテストへエントリー」を選択すると `contestId` が付与される。

```
contests/{contestId}
  creatorId, title, description,
  entryDeadline, votingDeadline,
  createdAt, updatedAt

contests/{contestId}/votes/{userId}          ← コンテスト単位で1人1票（下記5.）
  postId, updatedAt

posts/{postId}
  # 既存フィールドに加え、コンテストへのエントリーの場合のみ意味を持つフィールドを追加
  caption, imageUrls, latitude, longitude, createdAt,
  userId,           // 通常投稿は常に設定。コンテスト投稿は匿名解除まで未設定（下記3.）
  contestId,        // 通常投稿は未設定。コンテストへのエントリーの場合のみ設定
  stayAnonymous,    // bool、既定 false。contestId が設定されている場合のみ意味を持つ（下記4.）
  voteCount,        // 非正規化カウント、既定 0。contestId が設定されている場合のみ意味を持つ

posts/{postId}/private/author   ← 単一ドキュメント（id: "author"）。contestId が設定されている投稿にのみ存在
  userId

posts/{postId}/comments/{commentId}  ← 既存 Comment / CommentService をそのまま流用（下記6.）
```

位置情報（`latitude`/`longitude`）は通常投稿と同じく投稿時必須とする。コンテストへのエントリーも最初からフィード・マップに表示するため（下記4./7.）、投稿方式を分けて位置情報を省略できるようにする理由がない。

### 3. 匿名性の実装：`userId` をサブドキュメントに分離し、解除時に本体へ書き戻す

Firestore のセキュリティルールはドキュメント単位でしか読み取り制御できず、フィールド単位で「このフィールドだけ隠す」ことはできない。そのため `contestId` が設定された投稿は、匿名期間中は `posts/{postId}` 本体に `userId` を含めず、`posts/{postId}/private/author` という別ドキュメントに分離する。`users/{uid}/private/profile` と同じ設計パターン。通常投稿（`contestId` 未設定）は従来どおり `userId` を本体に直接持ち、この分離の対象外。

読み取り権限（`private/author`）：

- 管理者：常に可
- 本人（`private/author.userId == request.auth.uid`）：常に可
- それ以外：不可（本体の `userId` が下記の書き戻しにより公開されるため、`private/author` 自体を一般公開する必要はない）

匿名解除（下記4.）のタイミングで、Cloud Functions が `private/author.userId` の値を `posts/{postId}.userId` に書き戻す。これにより、解除後は通常投稿と全く同じ経路（`userId` からユーザー情報を解決する既存のフィード/マップ表示ロジック）でそのまま表示できる。`stayAnonymous == true` の場合は書き戻しを行わず、`userId` は永続的に未設定のままとする（管理者は `private/author` 経由で常に把握可能）。

匿名期間中に投稿者本人が自分の投稿を編集・削除できるよう、クライアントは「自分のコンテスト投稿かどうか」の判定を `private/author.userId` の読み取り成否で行う（本体の `userId` は空のため使えない）。

表示は「表示上匿名」であり、完全匿名（管理者含め特定不能）ではない。規約違反や不正投票への対応のため、管理者はモデレーション目的で常に投稿者を把握できる。

### 4. フェーズ判定と匿名解除・フィード/マップ反映

**フェーズは保存フィールドではなく、`entryDeadline` / `votingDeadline` と現在時刻（`request.time`）から都度算出する。** 状態遷移の手動操作や切り替え忘れを避けるため。

| フェーズ | 条件 | エントリー投稿 | 投票 |
|---|---|---|---|
| エントリー中 | `now < entryDeadline` | 可 | 不可 |
| 投票中 | `entryDeadline <= now < votingDeadline` | 不可 | 可 |
| 終了 | `now >= votingDeadline` | 不可 | 不可（閲覧のみ） |

コンテストへのエントリーは投稿された瞬間から通常のフィード・マップに表示される（`contestId` が設定されているだけの通常投稿として扱われるため、表示自体を止める理由がない）。ただし匿名期間中は `userId` が空のため、投稿者名の代わりに「匿名」等のプレースホルダーを表示する。`contestId` の有無で、フィード・マップ・投稿詳細のいずれにも「コンテスト参加中」を示すタグを常時表示する（匿名解除の前後を問わない）。

投稿者名公開は、エントリー投稿時に本人が選択する `stayAnonymous`（既定 `false`）で制御する。`votingDeadline` 経過を検知する Cloud Functions（スケジュール実行）が、`stayAnonymous == false` の対象投稿について `private/author.userId` を `posts/{postId}.userId` へ書き戻すことで匿名解除する。何もチェックしなければ終了後に匿名は解除される。「匿名のまま」チェックを入れた場合は終了後も恒久的に匿名を維持する（管理者のみ把握可能な状態が継続する）。

### 5. 投票：コンテスト単位で1人1票、非正規化カウント、投票の秘匿

投票ドキュメントは **投稿単位ではなくコンテスト単位** の1件（`contests/{contestId}/votes/{userId}`、`postId` フィールドを保持）とする。

検討の過程で、いったん `posts/{postId}/votes/{userId}` という投稿単位のサブコレクション案を検討したが、この構造では「1投稿につき1票」は保証できても「1コンテストにつき1票（他投稿への投票と排他）」を構造的に保証できないことが判明したため、コンテスト単位の単一ドキュメント方式に変更した。他投稿への投票の切り替えは、この1件のドキュメントを書き換えることで表現する。

- 投票・変更・取消は投票期間中のみ可能。コンテスト終了後（集計フェーズ）は変更不可。
- 自分の投稿への投票は不可。匿名期間中は本体の `userId` が空のため、`private/author.userId` との比較で判定する。
- 集計は `posts/{postId}.voteCount` の非正規化カウント（`ReactionService.toggleReaction` と同じトランザクション方式）。投票の新規作成・切り替え・取消のいずれも、旧投稿・新投稿の `voteCount` と `votes/{userId}` を同一トランザクションで更新する。
- `votes` サブコレクションの一覧（誰がどの投稿に投票したか）は非公開とし、管理者または本人のみ読み取り可能とする。一般メンバーが取得できるのは `voteCount` の集計値のみ。投票の秘匿性と同調圧力の回避を優先した。

### 6. コメント：既存 Comment / CommentService をそのまま流用（変更不要）

コメント主は匿名化の対象外（要件どおり「コメント主は把握可能」）。コンテストへのエントリーも `posts` コレクションの通常ドキュメントであるため、既存の `Comment` モデル・`CommentService`（`posts/{postId}/comments`）をそのまま使える。専用の `entries` コレクションを廃止したことで、`CommentService` の `postsCollection` 固定を一般化する対応は不要になった。

### 7. 表示場所：通常のフィード・マップに統合し、コンテスト専用画面は一覧・投票 UI に限定

コンテストへのエントリーは通常投稿と同じ経路でフィード（`feed_page`）・地図（`map_screen`）に表示され、「コンテスト参加中」タグで区別する。位置情報を伴う地図表示との相性が悪いという当初の懸念は、投稿時に位置情報を必須化する（上記2.）ことで解消する。

コンテスト専用の画面遷移（コンテスト一覧 → コンテスト詳細（エントリー一覧・投票）→ 投稿詳細（既存の投稿詳細画面を再利用し、投票 UI を付加）は維持する。これは「そのコンテストのエントリーだけを集めて投票できる場」を提供するためであり、通常のフィード/マップ表示を代替するものではない。

### 8. エントリーの編集・削除

本人のみ、かつエントリー期間中（`now < entryDeadline`）のみ編集・削除可能。投票開始後に内容を差し替えられると投票の公平性が損なわれるため。匿名期間中の「本人」判定は `private/author.userId` に基づく（上記3.）。管理者はフェーズに関わらずいつでも削除可能（規約違反対応）。

## 影響（Consequences）

- 専用の `entries` コレクションを廃止したことで、投稿作成 UI・`PostService`・フィード/マップの表示ロジックは通常投稿と共通のまま拡張できる。一方で `Post` モデルに `contestId` / `stayAnonymous` / `voteCount` という、通常投稿では意味を持たないフィールドが追加され、`Post` の責務がわずかに肥大化する。
- 匿名解除を「フィールドの書き戻し」で実現するため、`votingDeadline` 経過を検知する Cloud Functions のスケジュール実行（Cloud Scheduler 等）が新たに必要になる。当初案（ルール側の条件付き `get()` のみで完結）よりインフラ・実装の複雑度が増す。
- `posts/{postId}` の `userId` がコンテスト投稿では一時的に欠損しうるため、既存の「投稿には必ず `userId` がある」という暗黙の前提を置いているクライアント側コード（通知、プロフィール集計、自分の投稿一覧など）を全て洗い出し、`contestId` が設定された投稿を安全に無視 or 別扱いできるか確認する必要がある。
- `private/author` の読み取り権限（本人・管理者のみ）と、書き戻し後の本体 `userId` の公開は同じ「匿名解除」という状態を二箇所（サブドキュメントの権限とスケジュール Functions の実行結果）で表現することになり、書き戻しに失敗・遅延した場合に「フェーズ上は終了しているが `userId` はまだ空」という一時的な不整合が起きうる。実装時はスケジュール実行の再試行・冪等性を担保する。
- 匿名投稿者の恒久非公開（`stayAnonymous == true`）を選べるため、管理者以外は永久にその投稿者を特定できない状態が発生しうる。規約違反時の対応は常に管理者経由になる。
- 投票の変更・取消をトランザクションで行うため、`ReactionService` より書き込み対象ドキュメントが多く（旧投稿・新投稿・votes ドキュメントの最大3件）、実装の複雑度がやや高い。
- コンテスト作成を管理者限定にしなかったため、乱立や荒らし目的の作成に対する抑止力は「管理者によるコンテスト削除」のみ。運用上の乱立が問題になった場合は、作成をレート制限する、あるいは管理者承認制に変更する等の追加対応を別途検討する。
